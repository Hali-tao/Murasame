- `first-formal-failed/`：第一次60秒运行，隔离代码经过执行和审阅后，场景内截图超时；该场景保留 failed，不改写为成功。

- `verified-sources/`：工具源码快照。`perf-suite.mjs.txt` 是正式三场景运行时版本；`final-perf-suite.mjs.txt` 另补非场景准备IPC超时和 Windows 本次进程树强制退出。计量 helper 与模型 fixture 在这两个版本间相同。最终短时复核另归档，不把不同版本拼成同一次正式运行。

- `final-smoke/`、`final-smoke-run.txt`：最后准备IPC超时和Windows树清理修改后的真实短时复跑，3 measured/2 blocked，正常停止回执 `cleanupSucceeded=true`、无清理错误、独立profile已移除，退出2；不是又一次60秒验收，也没有触发强杀分支。

## 复核和失败修复

独立复核发现并关闭：超时后迟到驱动继续请求批准、首份样本延迟挤占有效时长、清理 Result 失败漏报、清理阶段无超时、Windows 启动包装进程的子树清理、准备IPC没有超时。两项行为回归先失败（实际0.015秒小于要求0.04秒；超时后批准1次而非0次），修复后8项通过。最终异常进程强杀和 Docker 清理失败分支当前是静态复核，尚未做真实故障注入，不宣称已验证。

首次截图超时只复现一次；后续截图成功不足以解释原超时原因。新版本将截图移到测量窗口后，独立记录 captureIssues 和当时窗口/空闲状态，不用截图开销污染资源采样。原失败继续保留。

**目视检查另发现真实 UI 同步缺陷**：`formal-three-scenes/autonomy-completed.png` 虽成功保存，但自主活动页面仍显示“活动未开始”，与同份JSON中真实 `running`、核验产物和输出385不一致。这张图是缺陷证据，不能作为界面显示正确的证据。当前 AutonomyPage 仅在本页按钮回调中更新状态；初始未运行时不轮询，也没订阅现有 `onStatusChanged`，因此其他入口启动后不会更新。本轮尚未修改生产页面；下一轮优先用页面已打开、从其他入口启动/停止的回归修复。顶部模型标签同样不会因直接IPC配置刷新；该标签目前仅在测量路径观察到，不能据此扩大为正常UI配置有缺陷。

这里的“其他入口”已验证的是公开IPC调用；当前源码中正常用户启动仍来自本页按钮并会 apply 状态。尚未复现从正常按钮启动也不同步，不扩大缺陷范围。

复跑：`node scripts/perf-suite.mjs --isolation --executable=release/overnight-2026-10-29-sixth-delivery/win-unpacked/Murasame.exe`。默认60秒/场景、15秒预热；输出在新建时间目录。`--seconds=2` 仅诊断。未给 `--isolation` 时不会启动容器；环境未就绪时明确阻塞，不自动构建。
