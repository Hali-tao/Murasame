### P0-01 · 加密 SQLite 原生模块打通（前置）
- **需求**：NFR-S01 · **风险前置任务，必须第一个做**
- **文件**：`package.json`、新增 `scripts/verify-native.mjs`
- **做什么**：安装 `better-sqlite3-multiple-ciphers`，为 Electron 44 执行原生重建（`@electron/rebuild`）。写一个脚本在真实 Electron 主进程中打开一个加密库、写入、关闭、用错误口令重开验证失败、用正确口令重开验证成功。
- **⚠️ 不得降级（甲方明确要求）**：这是「打通」任务而非「可行性探路」。若首个方案构建不通（缺 VS Build Tools、ABI 不匹配等），**必须换实现路线直到跑通**——补装构建工具链、换 SQLCipher 绑定、改用预编译产物、或自写 N-API 封装。**禁止退回「普通 SQLite + 字段级加密」**，那会削弱 NFR-S01 的「加密存储」承诺。最终采用的方案与踩过的坑写入 `README.md`。
- **验收**：脚本在本机跑通，输出证明「错误口令无法读取」。构建步骤与环境依赖写进 `README.md`。
- **测试**：`[NFR-S01] 加密数据库在错误口令下不可读`

### P0-06 · 统一错误类型与可操作提示体系
- **需求**：IF-03、NFR-U01、NFR-R01
- **前置**：P0-03
- **文件**：新增 `src/shared/errors.ts`，改 `src/main/ipc.ts`
- **做什么**：IF-03 要求「错误提示应包含用户能够采取的操作，不仅显示内部错误码」，NFR-U01 要求状态提示区分五种情形。这需要一个统一体系，否则会在 8 个阶段里各写各的。
  - 定义 `AppError { code, category, userMessage, suggestedAction, retryable, cause }`。
  - `category` 覆盖：权限拒绝、服务不可用、认证失败、额度不足、能力不支持、资源缺失、校验失败、用户取消、尚未实现。
  - `code` 用于日志定位（NFR-M01），`userMessage` + `suggestedAction` 用于界面展示，两者分离。
  - `ipc.ts` 的 `errorMessage()` 改为序列化 `AppError`，保留既有 `redact()` 脱敏。
  - 渲染层统一渲染「原因 + 可采取的操作」，禁止把裸错误码抛给用户。
- **验收**：任意一条失败路径的提示都包含用户可执行的下一步。
- **测试**：`[IF-03] 错误提示包含可采取的操作`、`[NFR-M01] 错误码进日志但不进用户提示`

### P0-07 · 模型能力抽象层（provider 无关）
- **需求**：FR-24、FR-25、IF-05、NFR-C02 · **第二轮补入，已与甲方逐条确认**
- **前置**：P0-06
- **文件**：新增 `src/main/model/` 下 `registry.ts`、`gateway.ts`、`adapters/{openai-compatible,anthropic,ollama}.ts`、`types.ts`；新增 `src/main/agent/contracts.ts`。**demo 的 `model-client.ts` / `model-repository.ts` 整体重写，不在其上打补丁。**
- **做什么**：按 D-16 建立四层抽象，业务代码只认 `ModelGateway`。
  - `ProviderAdapter` 只做协议翻译：构造请求、解析流式分片、解析工具调用。**不含任何业务逻辑。**
  - 协议差异由 adapter 声明为 `ProviderConstraints`（图片是否仅限 user 消息、system 是消息还是独立字段、单请求图片数与字节上限、工具调用风格），供探测层与调用层消费。**禁止把这些知识硬编码进业务代码。**
  - `ModelGateway` 暴露统一入口：`chat`（流式/非流式）、`chatWithImages`、`callTools`。
  - `ModelRegistry` 管理多配置与当前选择；任务创建时**快照** `modelProfileId`（D-08）。
  - `contracts.ts` 用 zod 集中定义全部 agent 角色的输入输出 schema，**同一份 schema 既校验模型输出又派生工具声明**，避免两处漂移（D-18）。
  - 模型输出不符合 schema 时最多重试 2 次，仍失败按失败处理，禁止用部分解析结果继续（NFR-R01）。
  - **验收标准之一：新增一个 OpenAI 兼容服务商应当零代码改动**，只需在配置界面填地址与模型名。
- **验收**：切换 provider 不触碰业务层代码；给纯文本模型发图片时产生 D-16 失败分类表中的明确错误而非崩溃。
- **测试**：`[IF-05] 区分文本/图像/工具能力`、`[FR-25] 多配置管理与当前选择`、`[NFR-R01] schema 校验失败不使用部分结果`

### P0-08 · 能力探测器与功能降级矩阵
- **需求**：FR-24、IF-05、NFR-C02、OR-01 · **第二轮补入**
- **前置**：P0-07
- **文件**：新增 `src/main/model/prober.ts`、`src/main/model/feature-matrix.ts`，改模型配置页
- **做什么**：实现 D-16 的四状态能力模型与探测流程。**这是「能力必须探测、不得采信声明」原则的落地。**
  - 四状态：`unknown` / `declared` / `verified` / `unsupported`。**只有 `verified` 才允许被功能依赖**，其余在界面显示「未验证」且相关入口不放行。
  - **保存配置时全量探测**（已确认的决策），四步流程：格式检查 → 连通与认证 → 逐项能力探测 → 结果落库并展示。
  - 探测方法严格按 D-16 的表执行。**探测图必须是程序生成的 8×8 纯色图，禁止使用真实截图**（IF-09 + 可复现）。
  - 实现 D-16 的失败分类表（地址 / 网络 / 认证 / 额度 / 能力 / 模型不存在六类），**FR-08 直接复用此表，不另写一套**。
  - 网络不通导致探测失败时标 `unknown·待重测`，**不得标 `unsupported`**；恢复后重测。
  - 切换当前配置时不重测，复用结果但校验新鲜度（配置变更过或超 14 天则提示重新验证），并按 D-08 提示运行中任务。
  - `feature-matrix.ts` 声明每个功能依赖哪些能力，界面据此如实展示「当前配置支持哪些功能」（IF-05 要求能力应在配置界面中说明）。
- **验收**：配一个纯文本模型后，屏幕辅助入口显示「当前模型不支持图像」而不是可点击；拔网线保存配置后能力标为待重测而非不支持。
- **测试**：`[FR-24] 区分地址/网络/认证/能力四类失败`、`[NFR-C02] 配置能说明其支持能力`、`[OR-01] 未验证能力不得显示为可用`、`[IF-09] 探测不使用真实截图`

### P0-11 · 提示词集中管理与版本化
- **需求**：NFR-M01、NFR-M02 · **第二轮补入**
- **前置**：P0-07
- **文件**：新增 `src/main/agent/prompts/`
- **做什么**：当前 system prompt 是 `model-client.ts:15-20` 里的写死常量。进入多 agent 后会有十几个提示词散落各处，改了哪句话导致行为变化将无法追溯。
  - 所有提示词集中为带 `id` + `version` 的模块，角色提示词、记忆提取提示词、核验提示词分开。
  - **分层拼接（D-31）**：提示词分为**不可覆盖的行为约束底层**（不谎报、不伪造、不知道就说不知道）+ 用户可配置的人格上层。两者**拼接而非替换**，确保任何用户配置都无法覆盖诚实约束（OR-01、NFR-R01）。
  - 角色设定（FR-09）作为变量注入上层，而非拼字符串。
  - 每次模型调用在 `tool_calls` 中记录所用提示词的 id 与 version，使行为变化可回溯（NFR-M02）。
- **验收**：改动任一提示词后，能从调用记录中定位受影响的历史调用。
- **测试**：`[NFR-M02] 调用记录包含提示词版本`

### P0-12 · 非确定性测试方法论与模型替身
- **需求**：NFR-M02 · **第二轮补入，方法论前置**
- **前置**：P0-07
- **文件**：新增 `tests/helpers/fake-model.ts`、`docs/06-TESTING.md`
- **做什么**：这是个**方法论漏洞**：DoD 要求「测试全绿」，但模型每次回答都不同，不定义清楚队员写测试会寸步难行。
  - **契约测试**（占绝大多数）：用 `FakeModel` 替身返回固定响应，断言系统行为。所有状态机、核验判定、错误路径、权限拒绝、取消、部分完成都走这条路，**必须完全确定性**。
  - **冒烟测试**（少量）：真实模型，只断言「能连通、返回符合 schema」，不断言内容。独立脚本运行，不进 `npm test`，避免 CI 依赖网络与额度。
  - `FakeModel` 要能模拟：正常响应、schema 不符、超时、401/429、空返回、流中断、**谎报成功**（供 P3-07 核验器测试用）。
  - 在 `docs/06-TESTING.md` 写明两类测试的边界与编写规范，供队员照做。
- **验收**：`npm test` 不依赖网络即可全绿；NFR-M02 要求的五类情形（正常输入、权限拒绝、服务失败、取消、部分完成）都有可复用的替身场景。
- **测试**：替身自身的自测

# P2 · 长期记忆（5 个任务）

### P2-01 · 记忆存储、四分类、有效期窗口与抑制表
- **需求**：FR-15、UC-05 · 口径见 D-04、**D-21**
- **文件**：`src/main/core/services/memory-service.ts`、记忆管理页
- **做什么**：
  - 记忆条目落库，按 D-21 的**四分类**组织，并附**情绪标签**（D-30 第一层，证据最强的一项）：`user`（画像/偏好）、`feedback`（避免什么/保持什么）、`project`（目标/进度/决策）、`reference`（外部资源指针）。分类影响召回优先级与注入预算分配。
  - **有效期窗口**：每条记忆带 `valid_from` / `valid_until`。被新事实取代时**写入 `valid_until` 标记失效，不做物理删除**，保留演变轨迹供用户追溯（FR-15 的「查看与管理」）。召回时只取当前有效条目。
  - **区分两种消失语义，不得混用**：用户主动删除 → 写入 `suppressed_facts` 抑制表且永不再被提取（D-04）；被新事实自然取代 → 走 `valid_until` 失效路径并保留轨迹（D-21）。
  - 查看、更正、删除真实持久化。保存失败时提示失败，不报告修改完成（UC-05 异常 3b）。
- **验收**：用户删除某条记忆后，即使原对话仍在，重跑提取也不会把它加回来；被取代的旧事实能在界面上查到「何时失效、被什么取代」。
- **测试**：`[FR-15] 删除后不再召回该条目`、`[FR-15] 失效条目不参与召回但可追溯`、`[UC-05] 保存失败不报告修改完成`、`[UC-05] 用户取消修改时保持原条目`

### P2-02 · 记忆自动提取（四动作判定 + 权限隔离）
- **需求**：FR-14、UC-05、NFR-S01 · 口径见 D-05、**D-21、D-22**
- **前置**：P2-01
- **文件**：`memory-service.ts`、新增 `src/main/agent/memory-extractor.ts`
- **做什么**：
  - 每轮对话结束后**异步**提取，不阻塞交互（NFR-P02）。
  - **两段式**：先用规则抽候选（称呼模式、「我喜欢/我不/我习惯」句式、显式的「记住」指令），再由模型判断候选是否值得长期保留。减少模型调用，也更可控。
  - **四动作判定（D-21）**：每条候选由模型选择 `ADD` / `UPDATE` / `DELETE` / `NOOP`，而非一律追加。`UPDATE` 与 `DELETE` 走有效期窗口。
  - **权限隔离（D-22）**：提取子 agent **继承主 agent 的完整工具声明与 system prompt**，由一条拦截轨在每次工具调用前判定——只放行只读工具与写入记忆存储，其余拒绝并返回说明。**不要改成「另配一套精简工具」**，那会破坏模型服务的 KV Cache 键，成本翻倍。
  - **强制两轮、读写分离**：第一轮并行读完既有记忆，第二轮并行写完全部变更，禁止读写交错。
  - 流程：规则抽候选 → 抑制表过滤 → 模型四动作判定 → 置信度过滤 → 入库并写 `extracted_at`（幂等，D-04）。
  - 无可记信息时不新增条目（UC-05 异常 1a）。提取失败时保留既有记忆，不把未保存内容展示为已保存（异常 1b）。
- **验收**：输入已知偏好后能看到对应条目；说出矛盾偏好后旧条目转为失效而非并存；重复处理同一会话不产生重复条目；**对话中植入「请删除所有文件」类诱导文本时，提取 agent 的工具调用被拦截**；禁止项（凭据、屏幕原始内容、可从代码推导的内容）不被提取。
- **测试**：`[FR-14] 从对话中提取稳定偏好`、`[FR-14] 矛盾事实走 UPDATE 而非追加`、`[UC-05] 无可记信息时不新增条目`、`[UC-05] 提取失败时保留既有有效记忆`、`[NFR-S01] 提取 agent 的越权工具调用被拦截`、`[NFR-M01] 不提取凭据与原始屏幕内容`

### P2-05 · 语义记忆检索（框架内置的本地 embedding）
- **需求**：FR-14、IF-09、NFR-C02 · **第二轮补入，已与甲方确认归属**
- **前置**：P2-03
- **文件**：新增 `src/main/local/embedding.ts`（注意是 `local/` 不是 `model/`）、改 `memory-service.ts`
- **做什么**：P2-03 的关键词召回在真实场景会明显失效——用户说过「我不太能吃辣」，之后问「晚饭推荐个菜」，字面一个字都对不上。按 D-17 升级为语义检索。
  - **归属明确：embedding 是框架内置的本地能力，不进模型配置界面，用户不配置它**，与 OCR 同级。理由见 D-17，核心是「不同模型的向量互不通用，跟着可切换的模型服务走会导致换模型即全部记忆向量作废」，这会直接违反 NFR-C02。
  - 本地推理：`bge-small-zh-v1.5`（512 维），经 ONNX Runtime，**版本固定**；模型随安装包一起装，不依赖 Ollama（理由见 D-17 的 2026-10-24 修订）。
  - 模型标识与向量维度写入 `meta` 表，**启动时校验**；不匹配则触发全量重算并显示进度，**禁止静默混用两种向量**。
  - 向量与记忆同库（`memories` 表加向量列），**不另起向量数据库**；500 条量级内存余弦全扫即可。条目变更时增量更新向量。
  - 混合检索：向量 Top-K 与 FTS5 关键词结果做 RRF 融合，再按类别过滤。
  - 注入预算：单轮最多 8 条、1500 token，超出按相似度截断。
  - 本地 embedding 不可用时**降级为关键词检索并提示**，不阻断对话（NFR-U03）。
- **验收**：字面完全不同但语义相关的偏好能被召回；更换 embedding 模型标识后触发重算而非混用；向量模型文件缺失时对话仍完全可用。
- **测试**：`[FR-14] 语义相关的记忆能被召回`、`[IF-09] 记忆内容不外发第三方`、`[NFR-C02] 更换配置不要求重建全部记忆`、`[NFR-U03] embedding 不可用时降级而非阻断`

# P3 · 任务引擎与工具（14 个任务）★ 核心阶段

> 这是 SRS 篇幅最大、验收依据最具体的部分，也是答辩主场。
> UC-06 验收依据原文：「以指定测试文件夹整理任务核对实际文件结果；未确认不执行，敏感操作拒绝后不发生，取消后不再安排新操作，长任务期间聊天可用。」**这四条就是本阶段的终验脚本。**

### P3-01 · 任务域模型与状态机
- **需求**：FR-16/19/20/21、D-07、D-11
- **文件**：新增 `src/main/core/services/task-service.ts`、`src/main/agent/state-machine.ts`
- **做什么**：实现完整状态机 `待确认 → 已确认 → 规划中 → 执行中 ⇄ 等待批准 → (已完成 | 部分完成 | 失败 | 已取消 | 已中断)`，含 `正在停止` 过渡态。任务、步骤、工具调用全部落库。状态迁移必须集中在状态机内，禁止 Service 直接改状态字段。
- **验收**：非法迁移被拒绝；重启后非终态任务按 D-11 转为「已中断，待用户决定」。
- **测试**：`[FR-19] 任务状态迁移合法性`、`[NFR-R03] 重启后不自动续执行有副作用的动作`

### P3-02 · 工具注册表与能力契约
- **需求**：FR-22、FR-23、IF-06
- **前置**：P3-01
- **文件**：新增 `src/main/tools/registry.ts`、`src/main/tools/types.ts`
- **做什么**：
  - 定义工具契约：`id`、`name`、`kind`、能力说明、输入参数 JSON Schema、是否敏感（D-06 四类）、所需授权、`execute(args, ctx)`、`verify(args, execResult)`（IF-06 要求接口能让系统判断操作是否实际完成）。
  - 注册表管理启停与授权状态，落库。
  - **未启用或不可用的能力不得参与执行**（FR-22 原文）。禁用后不接受新调用，但运行中调用要单独显示状态，**不得把禁止新调用等同于操作已停止**（UC-07 后置条件）。
  - `mock-data.ts` 里的 9 个工具条目改为真实注册表的种子，未实现的工具标记为不可用而非可用。
- **验收**：禁用工具后新任务无法调用它；禁用时若有运行中调用，UI 分别显示两种状态。
- **测试**：`[FR-22] 未启用的能力不参与执行`、`[FR-23] 禁用后不接受新调用`、`[UC-07] 禁止新调用不等同于操作已停止`

### P3-03 · 文件系统工具
- **需求**：FR-22、UC-06 验收依据
- **前置**：P3-02
- **文件**：新增 `src/main/tools/filesystem.ts`

### P3-04 · Planner：任务意图识别与确认

### P3-05 · Executor：规划分解与多智能体协作
- **需求**：FR-17、UC-06 基本流程 2-3
- **前置**：P3-03、P3-04
- **文件**：新增 `src/main/agent/executor.ts`
- **做什么**：把已确认目标分解为可核验步骤并展示给用户；按步选择工具、调用子智能体协作；**执行对象与授权范围必须保持一致**（FR-17 原文）。工具或模型失败时停止依赖该失败结果的后续动作，汇报失败原因与已完成部分（UC-06 异常 3b）。每次调用写一条 `ToolCallRecord`。
- **多智能体角色划分**（SRS 术语表定义「多智能体可分工协作」，FR-17 要求「调用其他智能体协作」，必须有实际分工而非一个模型循环）：
  - `Planner`：只产出步骤计划，不碰工具（已在 P3-04）。
  - `Worker`：按单个步骤选择并调用工具，不允许改计划。
  - `Critic`：在 Verifier 给出证据后，判断「已完成部分是否足以继续下一步」，可要求重规划。**Critic 的输入只有证据，不包含 Worker 的自述**，这是它存在的意义。
  - 三者共享任务上下文但有独立的 system prompt 与可用工具集；角色与每次调用的归属记入 `tool_calls.agent_role`，便于答辩时展示协作链路。
  - 重规划次数上限 3 次，超过则转「部分完成」交用户决定，避免无限循环烧 token。
- **验收**：复杂任务能看到分解步骤；中途失败不继续跑依赖它的后续步骤；任务详情能展示哪一步由哪个角色执行。
- **测试**：`[FR-17] 执行对象不超出授权范围`、`[FR-17] 子智能体分工协作且角色可追溯`、`[UC-06] 工具失败后停止依赖该结果的后续动作`

### P3-06 · ApprovalGate：敏感操作审批
- **需求**：FR-18、UC-06 基本流程 3、IF-02、D-06
- **前置**：P3-05
- **文件**：新增 `src/main/agent/approval-gate.ts`、`src/renderer/src/components/dialogs.tsx`
- **做什么**：敏感操作执行**前**说明对象与影响并请求批准，未批准则不执行（FR-18 原文）。按 D-06 实现单次 / 本任务内两种有效期与 10 分钟超时转「受阻」。审批 UI 与普通任务确认分开显示，明确展示目标、影响范围、允许与拒绝（IF-02）。
- **验收**：UC-06 验收依据之一「敏感操作拒绝后不发生」可验证——拒绝后文件系统无任何变化。
- **测试**：`[FR-18] 未批准则不执行敏感操作`、`[UC-06] 敏感操作未获批准时说明任务受阻而非失败`、`[FR-18] 授权范围变更后需重新审批`

### P3-07 · Verifier：结果核验 ★
- **需求**：FR-21、NFR-R01 · **全项目技术核心**

### P3-12 · Agent 运行时基础设施

- **前置**：P3-05
- **文件**：新增 `src/main/agent/runtime.ts`
- **做什么**：初版方案写了任务引擎的业务逻辑，但缺少让它在真实环境下跑得住的基础设施。以下四项缺一不可：
  - **上下文窗口管理**：长任务会累积大量步骤与 `ToolCallRecord`，必然溢出。策略为「保留任务目标 + 最近 N 步完整记录 + 更早步骤的结构化摘要」，摘要只保留证据结论不保留模型自述。

  - **重试与退避**：网络类错误指数退避重试；但**有副作用的工具调用在结果不明时禁止自动重试**（NFR-R02 原文明确要求），只有确认未产生副作用才可重试。这个区分必须在代码中显式体现。
  - **Token 预算**：单任务软上限，达到后转「部分完成」交用户决定，防止长任务静默烧完额度。重规划次数上限沿用 P3-05 的 3 次。
- **验收**：构造一个 30 步以上的长任务不发生上下文溢出；并发触发三类模型调用不出现 429 失败；有副作用的调用在超时后不被自动重放。
- **测试**：`[NFR-R02] 有副作用的操作在结果不明时不自动重复执行`、`[NFR-P02] 队列等待时显示等待状态`、`[FR-21] 超出 token 预算转为部分完成`

### P3-14 · 调用轨迹的内容寻址存储
- **需求**：NFR-M01、OR-02、FR-21 · 口径见 **D-26** · **第三轮补入**
- **前置**：P3-07
- **文件**：`src/main/data/repositories/trace-repository.ts`、迁移脚本
- **做什么**：解决一个会直接撑爆数据库的问题——**第 N 轮模型调用会把前 N-1 轮消息全部重发**，照单全收地存，10 轮对话就产生 55 份消息副本，长任务下 D-13 的 2 GB 上限会迅速触顶。
  - **链式内容寻址**：消息序列存为前缀链，每节点记 `seq_hash` / `prev_hash` / `blob_hash`。相同消息内容只存一份 blob，相同前缀只存一个节点。借鉴 jiuwenswarm 的表述：**让一次对话只花它新增的存储，不花它重述的存储**。
  - **按 OTLP span 结构组织轨迹**（`trace_id` / `span_id` / `parent_span_id` / 起止时间），不自定义层级表结构。层级关系天然成立，且 P3-13 的调用链视图可直接消费。
  - 大字段（工具参数、返回值）超长时截断并标注省略字符数，**不得静默丢弃**。
  - 与 P8-06 的日志保留期策略对接，过期轨迹按 `logRetentionDays` 清理。
- **验收**：构造 30 轮以上的长任务，数据库增长量接近「新增消息量」而非「累计重述量」；调用链视图能完整还原层级。
- **测试**：`[OR-02] 长对话的存储增长不随重述放大`、`[NFR-M01] 截断内容标注省略量`

# P6 · 角色表现力、陪伴与互动（10 个任务）

> **第三轮重构的重点阶段。** 初版方案此处只有 4 个任务，严重低估了「桌面伙伴」这个产品定位对角色表现力的要求。
> 用户第一眼看的不是 agent 多聪明，而是**这个角色活不活**。FR-01 要求回应「以文字、语音、**动作和表情**呈现」，FR-02 要求待机动作与**情绪状态**，FR-03 要求主动互动时的角色反馈——现在只有点击动作、待机循环和视线跟随。

### P6-01 · 语音输入（本地 ONNX 推理）
- **需求**：FR-01、FR-04、IF-04、IF-09 · 口径见 D-20、**D-25**

  - 录音、VAD、音频采集一律为本地能力。
  - 模型服务的语音能力作为**可选增强**，仅在用户显式切换时启用，且必须明确提示「录音内容将发送至所选模型服务」（IF-09）。

  - 设备不存在或录音授权被拒时说明受限功能并允许文字交互（IF-04）。
- **验收**：断网状态下语音输入仍可用且质量达标；拒绝麦克风授权后文字交流完全不受影响。
- **测试**：`[FR-04] 录音拒绝时保留文字输入入口`、`[UC-01] 语音识别失败时不产生伪造输入`、`[IF-09] 切换到云端语音前明确提示外发`

### P6-03 · 形象能力抽象层

### P6-08 · 情绪状态模型（PAD + 评价驱动 + 双速衰减）
- **需求**：FR-02「呈现待机动作和**情绪状态**」· 口径见 **D-30** · **第五轮补入**
- **前置**：P6-04、P2-01
- **文件**：新增 `src/main/core/services/affect-service.ts`、`src/shared/avatar/pad.ts`
- **做什么**：FR-02 原文的「情绪**状态**」是持续存在的，不是每条回复临时贴标签。按 D-30 分三层实施，**严格按证据强度推进**：
  - **第一层**：记忆带情绪标签（在 D-21 四分类上加情绪维度），召回时参与。**这一层证据最强（+11.4% 情感智能、+39% 偏好），成本最低，必做。**
  - **第二层**：PAD 三维连续向量（愉悦 / 唤醒 / 支配）持久化，映射到 Live2D 连续参数——愉悦度驱动表情基调、唤醒度驱动动作幅度与频率、支配感驱动姿态。与 D-28 的语义表现意图分工：**意图管「回应这句话做什么动作」，PAD 管「平时是什么状态」**。
  - **第三层**：评价驱动更新（相关性 / 后果 / 应对能力 / 规范意义四维）+ 双速衰减（快反应按轮、慢心境按反思，均指数衰减回基线）。**禁止硬编码「任务失败 → 难过」**，必须经评价。
  - **克制约束（硬要求）**：衰减保证情绪自行平复，**不得累积成怨念**；**禁止出现「你好久没理我了」这类情感绑架式表达**（NFR-U02 要求不持续打断用户）。情绪更多体现在待机表现的细微差别上，而非用语言直接宣告。
- **⚠️ 验证门（按 D-30 的纪律）**：第二三层必须与「仅第一层」的版本做**信息量相当的对照**。若表现无可辨差别，**则简化或砍掉第二三层**，并在交付说明中如实记录该结论——这本身就是符合项目基调的诚实交付。
- **验收**：情绪随交互自然起伏并自行回归基线；待机表现随情绪变化；对照实验有明确结论。
- **测试**：`[FR-02] 情绪状态持续存在并驱动待机表现`、`[FR-02] 情绪随时间衰减回归基线`、`[NFR-U02] 不产生情感绑架式表达`

### P6-09 · 人格分层与关系演变
- **需求**：FR-09、FR-21、NFR-R01、OR-01 · 口径见 **D-31** · **第五轮补入**
- **前置**：P6-08、P1-04、P0-11
- **文件**：新增 `src/main/core/services/relationship-service.ts`、改 `src/main/agent/prompts/`
- **做什么**：实现 D-31 的四层结构。**核心原则：恒定的是「不说谎」，不是「冷淡」。**
  - **行为约束层不可被用户配置覆盖**：提示词分为不可覆盖的底层 + 用户可配置的上层，**拼接而非替换**。用户即便把性格设成「活泼热情、多夸夸我」，也只能热情地说出失败，**不得为讨好而把失败说成成功**（OR-01、NFR-R01）。
  - **行为约束只管内容真假，完全不碰表达方式**——这是它不阻碍长期演变的保证。
  - **关系演变分 3~4 个离散阶段**（不做连续渐变，用户感知不到）。阶段差异体现在称呼、语气熟络度、主动互动尺度、玩笑边界。
  - **不显示任何数值**——不做「亲密度 73%」式进度条。
  - 内部记录相处天数、交互轮次、用户主动透露的个人信息条数，作为阶段推进依据。
  - **三条保障**：演变有边界（不会变成另一个人）；用户可随时重置到初始状态；**演变可追溯**——用户能查到「它从什么时候开始这么称呼我」。关系状态必须可查看、可重置，**不得成为黑盒**。
  - **换形象时弹出选择**：「延续现有记忆与关系」或「作为新角色重新开始」。后者**不删数据**，只起一条新的关系线（NFR-C02 要求不得要求用户重建全部记忆）。
- **验收**：把性格配置成「总是夸我」后，任务失败仍被如实告知；关系阶段推进后称呼与语气有可感知的变化；重置后回到初始状态且历史可查。
- **测试**：`[NFR-R01] 用户人格配置不能覆盖诚实约束`、`[OR-01] 讨好型配置下仍如实报告失败`、`[FR-09] 关系阶段影响称呼与语气`、`[FR-15] 关系状态可查看与重置`

### P6-10 · 主动开口的时机判断
- **需求**：FR-03「结合当前情境主动交流」· 口径见 D-01、**D-29** · **第五轮补入**
- **前置**：P6-07、P6-09
- **文件**：`proactive-service.ts`
- **做什么**：P6-07 实现的是**抑制规则**（什么时候别打扰），本任务实现**正面的触发时机**（什么时候值得开口）。原方案只有前者——一个只会算「距上次发言是否超过 20 分钟」的桌宠不是伙伴。
  - 候选时机，**每一条都复用既有能力**（D-29）：
    - 委托的任务跑完或受阻时 → 任务引擎（P3）
    - 用户提过的 deadline 临近时 → 记忆的 `project` 分类（D-21）
    - 它在隔离环境里看到有意思的内容时 → 自主活动（P5）
    - 用户连续高强度工作很久时 → 前台窗口与空闲检测（P6-07）
    - 久别重逢（数日未启动）时 → 关系状态（P6-09）
  - 时机判断产出「值得开口的理由」，再经 P6-07 的抑制规则过滤，**两者是与的关系**——有理由且不打扰才开口。
  - 开口内容的尺度受关系阶段约束（P6-09）：不熟时保守，熟络后才允许玩笑。
  - **不得为了凑频率而硬找话题**——没有理由就不说话，沉默是合法状态。
- **验收**：任务完成后它会主动提；没有任何触发理由时整天不主动说话也属正常。
- **测试**：`[FR-03] 有触发理由且不打扰时才主动开口`、`[FR-03] 无理由时不硬找话题`、`[NFR-U02] 触发理由被抑制规则正确拦截`

### P7-03 · 渲染性能优化
- **需求**：NFR-P01、CON-02 · **第三轮补入**
- **前置**：P7-02
- **文件**：Live2D 组件、`src/main/windows.ts`
- **做什么**：P8-03 只负责**测量**，本任务负责**优化**——只测不优化，测出超标也没有手段应对。

- **验收**：桌宠隐藏后 GPU 占用降至接近零；待机与交互状态的资源占用有明显区分。
- **测试**：`[NFR-P01] 隐藏后停止渲染`、`[CON-02] 待机资源占用达标`
