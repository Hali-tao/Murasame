# 对话进行中修改模型配置：状态与回复完整性

## 已复现的问题

对话在发出请求时取得模型配置，但收到响应后只用配置ID更新连接状态。期间同一配置可以被修改、重新验证或删除：

- 修改服务地址、模型名称、服务商或密钥后，旧请求的成功/失败会把新配置误标为在线/离线；先改走再改回也会发生。
- 重新验证已经成功，较早的聊天请求随后失败，又把已验证配置改成离线。
- 等待回复时删除配置，回复已写入历史后，更新连接状态抛出“模型配置不存在”，使本次返回失败、页面收不到完整回复。
- 连接状态落盘失败也可能盖过本来有效的回复或原始网络错误。

旧安装包 `continuous-2026-10-29-autonomy-sync` 的两个实际端到端用例明确失败：重新验证完成后晚到的503使状态变离线；删除配置后聊天界面仍只有“我在。”，没有显示完整回答。第二个场景的历史落盘与界面交付差异另有真实SQLite单元验证。

首次端到端尝试先发聊天、再等重新验证，卡在验证按钮：流式探测与聊天共用串行队列。这次不是修复的红证据。调整用例为先等待验证的后续工具探测，再发聊天、释放验证并确认新的持久化探测时间，最后释放旧聊天响应；没有修改生产队列或绕过验证。

## 修复方式

注册表私下记录每份已解析配置所属的连接版本，聊天报告成功或失败时带回原对象。配置连接信息成功变更、成功重新验证或删除后，旧报告不再写入当前状态；新输入密钥也按既有“待重新验证”语义失效旧报告，不依赖加密字节是否恰好相同。只改显示名称或切换当前配置保留原连接的有效报告。

状态记录属于回复后的辅助更新，其失败不再撤销已保存回复，也不替换原始请求失败原因。会话删除、空回复和消息事务失败仍沿用原有检查。版本和对象关联只在内存中存在，不给配置、会话或日志增加密钥副本，也不修改数据库结构。
